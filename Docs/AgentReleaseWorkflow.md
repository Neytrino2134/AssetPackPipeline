# Команда агенту «пуш + обновление»

Это запрос на полный выпуск: подготовить актуальные изменения, повысить версию,
проверить, собрать, закоммитить, отправить main/тег и опубликовать установочный Release.
Один push без Release не считается выполнением такого запроса.
Обычная команда «только push» не публикует Release.

## Один раз на компьютере разработчика

GitHub CLI подготовлен в Saved/ReleaseTools/gh.exe из официального cli/cli Release,
SHA256 проверен. Для публикации требуется отдельная авторизация CLI — вход в
GitHub Desktop её не заменяет. Пользователь запускает Tools/GitHub-Login.cmd и
самостоятельно проходит вход через браузер. Не запрашивать токены в чате, не читать
файлы с токенами и не передавать ключи в командной строке или репозитории.
На устройствах пользователей плагина CLI/Git по-прежнему не нужны.

## Действия агента

1. Проверить git status/diff и origin. Включить все относящиеся к выпуску изменения,
   включая Resources с новым логотипом. Не включать несвязанные пользовательские файлы.
2. Если пользователь не задал инкремент, использовать patch (+0.0.1). Для новой
   функции выбрать minor, если это согласовано задачей. Уже опубликованный тег
   не перемещать: после 0.27.0 нужен новый номер, например 0.27.1.
3. Обновить `.uplugin`, `__version__`, README и создать release notes в Docs.
   Прогнать соответствующие изменениям проверки в реальном хосте, когда они нужны.
4. Сделать локальный коммит только проверенных файлов.
5. Запустить Python из Unreal с `Tools/publish_release.py --publish --notes-file
   Docs/ReleaseNotes-<версия>.md`. По умолчанию он запускает unittest, BuildPlugin,
   упаковку ZIP и генерацию манифеста. Для уже проверенной сборки разрешён явный
   `--binary-source <Win64>`. Без --publish только локальная подготовка.
6. Сценарий проверяет чистую main, origin, авторизацию, отсутствие опережающих
   удалённых коммитов, версии/хэши, соответствие тега HEAD. Выполняет atomic push
   main+тега; создаёт draft Release с ZIP/манифестом, скачивает их обратно, сравнивает
   содержимое и SHA256, затем публикует стабильный Latest Release.
7. Проверить публичный updater.check: на устройстве с более старой версией должна
   появиться available. Устройство с той же версией должно показывать current.
   В отчёте дать commit/tag/Release URL и указать реальные границы проверки.

Новая публикация требует пользовательского запроса на релиз/обновление;
самостоятельно опубликованные изменения без запроса не выпускать.
Сценарий не перезаписывает существующие Release/теги и не делает force push.
Если ошибка произошла после создания draft, он остаётся неопубликованным:
проверить результат, докачать/верифицировать недостающие файлы и только затем
продолжить вручную через агентский CLI. Повторный автоматический запуск
не должен скрывать или перезаписывать предыдущую попытку.

## Текущее состояние

Сценарий подготовлен; полноценная публикация ещё не проверена, потому что
GitHub CLI ожидает однократного входа пользователя. Новый логотип остаётся
подготовленным для следующего выпуска; архив/тег 0.27.0 не подменяется.
